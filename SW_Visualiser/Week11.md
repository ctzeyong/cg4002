### S2. How it works, in short

- **Authority.** The Player 1 phone is the host and runs all game logic (`MatchState`). Player 2's phone is the client: it sends requests (summon, spell with an aim) and draws what the host's `game/state` updates say. VS CPU runs the host logic locally. Damage, bridge choice, chasing, ranges, spell timing and mana are all decided on the host.
- **Positions** cross the network as fractions of the lane (`along`, `lat`), never as world coordinates, because the two phones do not share an AR space. Unit facing now travels the same way (`faceAlong`, `faceLat`).
- **Spells** share one aim (the crosshair floor ray, valid anywhere in the arena) and one number block (`SpellSpec`, registered by `SpellCaster`). A cast checks the lane, then the aim, then spends mana, so a miss costs nothing. A client sends the aim to the host, which re-checks mana and aim, runs the spell, and publishes it in a `strikes` list so both phones draw the same effect. Lightning is a telegraph then an instant area; Fireball is a flight, an area and a burn.
- **Combat** is host-simulated at 10 Hz. Each unit has a notice range, a hit reach and (ranged) an attack range, all multiplied by the arena scale. Units chase, lock one target, and deal `DPS x tick`. Lightning and Fireball are the only area damage.
- **Time to cross the lane** stays the speed definition for each unit (speed = lane length / seconds), so match pace is the same in any room.
- **Feel** (cursor art, sounds, music (menu, match, then a faster version in the last minute), vibration, banners, card pictures) is drawn and played locally on each phone and never changes the game state.

## 1. Two bridges

### 1.1 How it works today (why it is single-bridge everywhere)

| Where | What assumes one bridge |
| --- | --- |
| `MatchState.Geometry.CaptureHomeAnchorsIfNeeded` | One `bridgePosition`, `ownBridgeEdge`, `opponentBridgeEdge`, all on the lane axis. |
| `MatchState.Geometry.HalfWidthAt` | One width profile along the lane: island, then a smooth funnel down to `laneSpineFraction`, then the bridge strip. The arena is one shape symmetric about the lane axis. |
| `ClampToArenaBounds`, `IsInsideArenaBounds` | Clamp lateral offset to `+/- HalfWidthAt`. A single interval around the axis. |
| `MatchState.Combat.SimulateTick` | Before `PastBridge`, units are pulled toward `closestSpinePoint` (the lane axis) with `centeringInfluence` falling off with distance to the one `bridgePosition`. This is the funnel. |
| `ComputeUnitHeight` | Only checks the longitudinal position against the one span, then asks `BridgeVisualizer.DeckHeightAt`. |
| `BridgeVisualizer` | Instantiates one prefab at `matchState.BridgePosition`, samples one deck profile. |
| `ToCanonical` / `FromCanonical` | Position as `along` / `lat` fractions of the lane. Does not care about bridges, so it survives the change. |

### 1.2 Plan

**Step A: data model.** Replace the single bridge fields with a small list.

```csharp
public struct BridgeLane { public float LateralOffset; public Vector3 Position, OwnEdge, OpponentEdge; }
BridgeLane[] bridges;   // 2 entries, at -offset and +offset from the lane axis
```

- New tunable on `MatchState`: `bridgeLateralOffsetFraction` (fraction of `LaneWidthMeters`, start around 0.3). `bridgeCount` stays a constant 2 for now; don't build for N bridges yet.
- `CaptureHomeAnchorsIfNeeded` fills the array. Keep `BridgePosition`, `OwnBridgeEdge`, `OpponentBridgeEdge` as the axis midpoint values for anything that still wants "the centre" (the HUD, bubbles, debug).
- The two bridges must stay **mirror-symmetric about the lane axis**. See the networking challenge below.

**Step B: arena shape.** `HalfWidthAt(along)` cannot describe two strips. Replace it with a function that answers a 2D question:

```csharp
bool IsInsideArena(float longitudinal, float lateral);
float ClampLateral(float longitudinal, float lateral, float lookAhead);  // nearest valid lateral
```

- Island sections: one wide interval as now (`islandHalfWidth`).
- Bridge section: two intervals `[c - w, c + w]` for each bridge centre `c`, `w = bridgeHalfWidth`.
- Funnel sections: the island interval narrows into the two strips. Simplest correct approach is to take the **union** of the island interval (shrinking with the funnel) and the two strip intervals, then clamp to the nearest point in the union.
- `IsInsideOwnTerritory`, `IsInsideArenaBounds`, `ApplyOutOfBoundsDamage` all go through the new function. Territory (summon zone) is unchanged: still the full-island-width rectangle.

**Step C: unit routing ("nearest bridge").**

- Add `int BridgeIndex` to `UnitState`. Assign it **once, at spawn**, as the bridge whose lateral offset is closest to the spawn's lateral offset.
- Tie-break for a spawn exactly on the axis: alternate, or pick by unit id parity. Do not use float comparisons that can flip.
- In `SimulateTick`, replace `closestSpinePoint` (lane axis) with the point on **that unit's bridge spine** at the same longitudinal position, and measure `distanceToBridge` to that bridge's `Position`. Everything else in the pre-bridge branch (`SmoothDamp` centring, `lookAhead`, clamp) stays.
- After `PastBridge` the unit homes on the live tower as today.
- Committing at spawn (not re-picking each tick) avoids units dithering between bridges when they cross the midline.

**Step D: visuals and height.**

- `BridgeVisualizer`: instantiate the prefab once per bridge. Give each instance its own deck profile. `DeckHeightAt(worldPosition)` picks the nearest bridge by lateral distance.
- `ComputeUnitHeight`: add a lateral check, otherwise a unit in the gap between bridges reads as "on the deck".
- `WaterVisualizer` and `TowerPedestalVisualizer` mention the bridge; check they don't assume the water gap is one strip.

**Step E: bot and bubbles.** The CPU bot picks a random spawn point; with nearest-bridge routing it needs no change, but check it uses both lanes so VS CPU doesn't always route one side.

### 1.3 Challenges

1. **Engage range vs. bridge separation.** `engageRangeMeters` is 0.8 m and the whole lane is only about 2 m. If the two bridges are closer than 0.8 m apart, `FindNearestEnemyInRange` will lock units on different bridges onto each other across the water and they will stop and "attack" through the gap. Either keep the bridge centres further apart than the engage range (hard at 2 m scale: the island is about 1.65 m wide), reduce the engage range, or only count enemies on the **same bridge** while on the bridge section (needs `BridgeIndex` on the enemy as well, which it has).
2. **Everything is sized for the 2 m scale.** Bridge strip today is `LaneWidthMeters * laneSpineFraction` = about 0.22 m. Two strips of that width plus a gap need roughly 0.9 m of the 1.65 m island width. It fits, but the funnel gets short and the layout gets cramped for 0.15 m units. May need `laneSpineFraction` down to about 0.15.
3. **Bridge visual width is not tied to the gameplay width.** `BridgeVisualizer` scales width by `widthMultiplier` on the prefab's own width, while gameplay width comes from `laneSpineFraction`. This already drifts with one bridge; with two it will be more obvious (units walking on air at the edges). Fix: derive the visual width from `LaneWidthMeters * laneSpineFraction` so there is one source of truth.
4. **Client and host mirror each other.** The two phones compute geometry from their own lane, with opposite directions, so left and right are swapped between them. Symmetric bridges make this a non-issue; an asymmetric layout (one wider, one offset) would put units on the wrong bridge on the client. `along`/`lat` positions stay valid because they are normalised by lane size, but verify on two devices.
5. **Balance.** Two lanes means more survivability for defenders to cover (a player has to look at both) and a Tank on one bridge can be ignored by units on the other. Tower HP, `towerCounterDps` and mana regen were tuned for a single choke point and may need re-tuning. The choke point was a main defensive element.
6. **Out-of-bounds damage.** `IsInsideArenaBounds` is used to punish players standing outside the arena. With the gap between bridges now a non-arena area, a player's tower standing there starts taking damage. Check the tower positions (on the lane axis) are still inside: they are on islands, so fine, but add a test.
7. **Never compiled.** The scripts have never been tested with two bridges in the editor; start with `bridgeCount` behind a toggle so the single-bridge path keeps working while this is built.

### 1.4 Suggestions

- Add a debug-menu toggle **Bridges: 1 / 2** to compare behaviour and to keep a fallback for demos.
- Draw the bridge strips in `TrackingDebugOverlay` as gizmos so the new arena shape can be checked without waiting for the models.
- Optional later: units re-route to the other bridge if theirs is blocked or they are far from it after spawn.
- Optional later: show a faint "lane tint" on the summon cursor so players see which bridge a unit will take before they summon.

### 1.5 Order of work

1. `BridgeLane` array and `CaptureHomeAnchorsIfNeeded`. 2. The new arena shape functions plus clamp. 3. `UnitState.BridgeIndex` and routing in `SimulateTick`. 4. `ComputeUnitHeight`. 5. `BridgeVisualizer` ×2. 6. Tune `engageRangeMeters`, offsets, widths. 7. Two-phone check.

## 2. Lightning rework (aimed AOE)

### 2.1 How it works today

- `SpellCaster.CastLightningCore` costs 4 mana and calls `matchState.DamageOpponentTower(180)`. There is **no aim**: it always hits the tower. On a client it sends `RequestRemoteSpell("lightning")` and the host applies `DamageOwnTower(RemoteLightningDamage)`.
- The yellow sphere burst is spawned at `WorldPositionFromNormalized(0.5f)` (the middle of the lane), only on the caster's phone. The defender sees nothing.
- The cost and damage are duplicated as constants in `MatchState.Network.cs` (`RemoteLightningManaCost`, `RemoteLightningDamage`), separate from the `SpellCaster` serialized fields. They can drift apart.
- The glove sends only the `z` gesture; `GestureBindings.Perform` calls `CastLightningStrike()` with no position.
- `SummonCursor` already casts a ray from the screen centre to the floor, but it clamps to `maxAimDistanceMeters` (4 m) and marks the aim valid only inside **own** territory.

### 2.2 Plan

**Step A: aim source.** Reuse the crosshair the player already has. The lightning lands where the crosshair is at the moment the cast is accepted.

- `SummonCursor` gets a second query, `AimedSpellPosition` / `IsSpellAimValid`: same floor ray, but valid anywhere inside the arena (`IsInsideArenaBounds`, now public or exposed through a wrapper), not just own territory. Own-territory validity for summoning is unchanged.
- The ring shows the lightning radius when the aim is in the enemy half or over the bridge, and the small summon ring in own territory. A single reticle that changes size is enough for the first version.

**Step B: cast with a position.**

- `SpellCaster.CastLightningStrike()` reads the aim position and calls `MatchState.CastLightningAt(world, caster)`. It fails with a clear reason (`NO AIM`) if the crosshair is off the floor or outside the arena, and **does not spend mana in that case**.
- Remote (client) path: extend the spell request with `hasAim`, `along`, `lat`. `GestureRequest` already has these fields for spawn requests, so it is a small change to `RequestRemoteSpell` and `ApplyRemoteGestureRequest`. The host converts with `FromCanonical`.

**Step C: AOE on the host.**

New `MatchState.CastLightningAt(Vector3 center, UnitSide caster)`:

- For each unit on the **opposite** side of the caster, if the flat distance to `center` is within `lightningRadiusMeters`, apply damage. Start with flat full damage; offer linear falloff as a tunable.
- Tower: if the target tower's centre is within `lightningRadiusMeters + towerRadius`, apply tower damage. Make it a separate, smaller value (`lightningTowerDamage`) so a lightning that clips the tower is not a free tower hit.
- Dead units are removed by the existing cleanup loop at the end of `SimulateTick` (`CurrentHP <= 0` then `UnitDespawned`); the attack loop already skips units that died in the same tick, so setting HP is safe. Don't remove units inside the spell itself.
- No friendly fire in v1.
- Remove the duplicated constants in `MatchState.Network.cs`; read cost, damage and radius from one place.

**Step D: visuals shared by both phones.**

- Replace the lane-midpoint sphere with a ground-ring telegraph at the impact point, then a bolt (`LineRenderer` zig-zag from above) and a flash. Use `SpawnEffect`'s approach (built from code, `Sprites/Default`).
- Both phones must see it. The host adds a small `fx` list to the state snapshot (`id`, `kind`, `along`, `lat`), and the client plays each new `id` once. Without this the defender never sees the strike they are being hit by.

**Step E: UI.** Update the Lightning card stats line (`CardHandUI`, currently `"{dmg} dmg"`) to read radius and damage.

### 2.3 Challenges

1. **Aim latency on the glove path.** The gesture goes glove, then BLE, then the Ultra96, then the SSH tunnel, then the phone. The player's head keeps moving, so the crosshair at arrival is not where they aimed when they did the gesture. Mitigations: keep a short ring buffer of recent aim positions and use the one from roughly the measured latency ago, and/or make the strike land after a short **telegraph** (0.4 to 0.6 s) so the target position is locked at cast and the player sees where it will hit. Measure the real latency before choosing.
2. **Aim is only a floor ray.** `Aim()` hits the floor plane at `GroundY`. Bridge height is tiny here so it is fine, but the ray distance limit (4 m) and the arena far half behind the enemy tower may be hard to reach with the phone pointed down at a table-size arena. Test at the real scale.
3. **Client-aimed targets across two coordinate spaces.** The two phones do not share a world frame; only `along`/`lat` crosses the network. A strike aimed at the enemy half has `along` > 0.5 on the caster's phone. Check `ToCanonical` / `FromCanonical` flip correctly for the client (they use `LocalIsPlayer1`). The existing spawn aim has never been verified on the client for the enemy half, since spawning is restricted to own territory; **lightning will be the first feature to send a cross-lane position.**
4. **Rejected cast should be free and clear.** The current flow spends mana first (`TrySpendMana`) then acts. With an aim check the order must be: validate aim, then spend. Otherwise a miss is silently paid for.
5. **Balance.** Unit HP: Warrior 150, Rogue 120, Mage 90, Tank 700, Hero 450. 180 damage in an area kills any group of Warriors, Rogues and Mages in one cast for 4 mana, which is cheap against 2 to 4 mana units. Expect to retune damage, radius and mana cost, and to give it a cooldown. Tanks and Heroes survive it, which is a reasonable counter.
6. **Tower rush trade-off.** Lightning used to be the burst tower damage. That role shrinks. Check the game still has a tower-finish option (Overcharge, bubble mana) once Lightning no longer reaches the tower reliably.
7. **Host vs. client trust.** The client sends an aim; the host trusts it. Fine for a capstone, but clamp the aim to the arena on the host.
8. **Defender feedback.** Without a warning the defender cannot react. The telegraph in Step D gives a fair-play window and ties in with the existing `BubbleWarningUI` banner style.

### 2.4 Suggestions

- **Lock-on assist.** Snap to the densest enemy cluster within a small radius of the crosshair, so a slightly late glove gesture still hits. Easy to add after the basic version works.
- **Two-stage aim.** The `z` gesture arms the spell, the next held crosshair or a second gesture confirms. More reliable for latency, but it needs an extra state and glove event, so keep for later.
- **Damage falloff** from the centre makes aiming matter without making a near-miss useless.
- **Cooldown** shared on the card hand (a simple radial fill), so the spell is not spammed at 4 mana each.
- Move spell numbers (cost, damage, radius, cooldown) into a single `SpellStats` block to stop the duplicate constants returning.

### 2.5 Order of work

1. One place for spell stats; remove the duplicates. 2. `SummonCursor` spell aim plus reticle. 3. `MatchState.CastLightningAt` and the aim check before spending. 4. Remote request carries the aim; host applies it. 5. Visuals: telegraph, bolt, snapshot `fx` list. 6. Card text. 7. Tune with the real latency, then two-phone check.

## 3. Interaction between the two features

- A lightning strike near the bridge catches units on one bridge but not the other. That is intended and makes bridge choice meaningful. Pick a default radius smaller than the bridge separation so one strike cannot hit both.

## 10. Damage vibration (added 2026-10-22)

### Design

A short pulse, never a continuous buzz.
- **Trigger:** your own tower losing HP: enemy units hitting it, an enemy Lightning, or you standing out of bounds. Your units dying does not vibrate.
- **Rate limit:** at most one pulse every 0.45 s while damage keeps coming, so steady damage ticks like a heartbeat.
- **Strength:** set by the damage taken since the last pulse. Under 6 is a light tap, 6 to 25 medium, over 25 heavy. An enemy Lightning (60 to the tower) is a heavy thump; a single Warrior chipping at the tower is light to medium.
- **Why not `Handheld.Vibrate()`:** it is one long fixed buzz (about half a second) with no strength control, so it cannot do a pulse.

### What was done

| File | Change |
| --- | --- |
| `Gameplay/Haptics.cs` (new) | `Haptics.Pulse(Light / Medium / Heavy)`. iPhone: a single Taptic Engine tap. Android: a short timed one-shot vibration (20, 40 or 70 ms at rising strength). Editor and other platforms: does nothing. On/off is saved on the phone. |
| `plugins/iOS/BridgeRushHaptics.mm` (new, copied to `My project/Assets/Plugins/iOS/`) | The few lines of native iOS code behind the iPhone tap. |
| `Gameplay/GameStateRenderer.cs` | Watches your own tower HP each frame and fires the pulse. New "Haptics" fields: on/off, minimum interval (0.45 s), light-below (6) and heavy-above (25) damage. It works the same on the host and on the client, since the client's HP comes from the host's updates. |
| `UI/DebugMenu.cs` | Match category: `Haptics: ON/OFF` and `Test pulse`, which cycles light, medium, heavy each tap so you can feel the three strengths. |

- Only the tower damage triggers a pulse. A pulse when one of your units is hit or dies is possible later, but with many units it could get noisy.

## 11. Design decision: summon position is a strategy (2026-10-22)

How it works: each unit type moves at a fixed speed (lane length divided by its seconds to cross). A unit summoned closer to the bridge has less distance to walk, so it reaches the enemy tower earlier than one summoned at the same moment further back. Summoning is allowed anywhere in your own territory and the mana cost is flat.

**Decision: this is intentional. Where you place a unit is part of the strategy** (forward for a fast push, back for a safer or later arrival). No distance surcharge, no shorter summon zone and no rally line. The old design's surcharge for summoning near the bridge is dropped on purpose.

### 12.2 How it works

**Who decides what.** The Player 1 phone is the host and runs `MatchState`. Player 2's phone is the client: it sends requests and draws what the host's `game/state` snapshots say. VS CPU runs the host logic locally. Damage, bridge choice, chasing and ranges are decided on the host only. Positions travel as `along` (fraction of the lane from Player 1) and `lat` (sideways fraction), never as world coordinates, because the two phones' AR sessions do not share a space.

**1. Two bridges** (`MatchState.Geometry`, `.Combat`, `BridgeVisualizer`).
- When the arena is captured, two sideways offsets are made (plus and minus 0.3 of the lane width). With `Two Bridges` off there is one offset at 0, which is the old single bridge.
- The walkable area is the union of one interval per bridge. On the open island each interval covers the whole island. Near the bridge it shrinks onto that bridge's strip (`FunnelBlend`, `ClampLateral`). This replaced `HalfWidthAt`.
- On the first tick a unit exists, `ChooseBridge` gives it the nearest bridge (a spawn exactly on the axis alternates). It is steered to that bridge's line and clamped to its strip. After the bridge it homes on the tower as before.
- The visualiser draws one prefab per bridge, each with its own deck profile, sized to the walkable strip.
- Why nearest, chosen once: it is predictable for the player, and re-choosing each tick would make units flip between bridges at the midline.

**2. Lightning** (`SpellCaster`, `MatchState.Spells`, `SummonCursor`).
1. `SummonCursor` casts a ray from the screen centre to the floor. It reports a summon aim (own territory only) and a spell aim (anywhere in the arena, including the water between bridges).
2. A cast checks the lane, then the aim, then spends mana, so a miss costs nothing.
3. The host and VS CPU call `QueueLightning`. A client sends the aim to the host, which re-checks mana and aim and queues an enemy strike.
4. `MatchState` raises `LightningStrikeStarted` and each phone draws the telegraph (area, closing ring), then the bolt, flash and shockwave, with a charge sound that rises and a crack at impact.
5. After 0.5 s the host applies damage to every enemy unit in the radius (full at the centre, half at the rim) and a smaller hit to the tower if it is in range. Dead units are cleaned up on the next tick.
6. The cost, damage, radius, telegraph and tower damage live in one `SpellSpec`, which `SpellCaster` registers, so a client's cast uses the same numbers on the host.
- Why a telegraph: it locks the target when the cast arrives, so glove and network delay cannot move the strike, and it gives the defender a warning.

**3. Combat: notice, chase, hit** (`MatchState.Combat`).
- Three distances per unit, all multiplied by the arena scale: **notice range** (0.4, how far it notices an enemy unit), **hit reach** (0.15 for melee, how close it must get to hit) and, for ranged units only, **attack range** (Mage 0.35, its own hit distance).
- A walking unit notices the nearest enemy within its notice range (a ranged unit notices at least as far as it can shoot). If that enemy is already within its reach, it stops and attacks. If not, it walks straight toward it and stops just inside its reach, and keeps the chase while the enemy stays in range plus a small gap.
- An attacker whose target moves out of reach chases it again. Before, a melee unit kept hitting a target that had walked away.
- Units on different bridges ignore each other (the water is in the way), except that a ranged unit may shoot across it if the enemy is within its range.
- Towers are unchanged: units stop at the stand-off (melee at the edge plus clearance, ranged at their range from the edge) and a unit hitting a tower does not look around.
- **Damage with several targets.** Each unit locks onto one enemy (the nearest when it noticed) and deals `DPS x tick` (0.1 s) to it only. No splash. Several attackers on one target add up. A unit does not switch to a closer or weaker enemy; when its target dies it picks the nearest on the next tick. Overkill is wasted. Units act in spawn order inside a tick, and a unit killed earlier in the same tick cannot hit back. Each unit attacking a tower removes its own damage and takes the tower's counter-damage (15 per second) separately, ranged units included. Lightning is the only area attack.
- Why: a ranged unit only has an advantage if it reaches further than the thing it fights, and melee units need to close the gap or they look idle next to an enemy.

**4. The ranged Mage.** `UnitStatsTable` has `AttackRangeMeters` (0 = melee). The host uses it for noticing, stopping and the tower stand-off. For the visuals, each unit in the snapshot carries `target` and `range`, so `GameStateRenderer` can fire a glowing `RangedBolt` from the Mage to its target on both phones every 0.6 s. The bolt is a picture only; damage stays continuous.

**5. Arena scale.** One number multiplies every distance in metres: `scale = (lane length / 2 m) ^ 0.5`, limited to 0.7 to 1.8. It follows the live lane smoothly while setting up and is frozen when the match starts. It scales unit height, notice range, hit reach, every attack range, tower clearance and size, lightning radius, bolt and marker sizes and aim reach. It does not scale real-world values (tag size, floor height, bubble lock distance, HUD). The time to cross the lane stays the speed definition, because it keeps match pace and balance the same in any room. At a 2 m lane the scale is exactly 1.
- Why the square root: full scaling would keep units looking the same speed in any room but make them huge in a big one; no scaling made them look too fast. The square root is the gentle middle (the exponent is a setting).

**6. Cursor and area art** (`ReticleArt`, `SummonCursor`). Sprites drawn from code with smooth edges: a summon marker, a spell-area disc, a plain ring and a screen crosshair. No image files.

**7. Sound** (`GameAudio`). Each sound is synthesised from code the first time it is needed (a clang, a swish, three bell notes, a boom and a fanfare for the five units; a rising charge and a crack with thunder for Lightning; a shimmer for Overcharge) and cached. Clip slots in `SpellCaster` and `GameStateRenderer` let you replace any with a real recording. Why synthesised: there were no audio assets and this needs no files; it plays on both phones.

**8. Haptics** (`Haptics`, `BridgeRushHaptics.mm`). A light, medium or heavy pulse when your own tower loses HP, at most once per 0.45 s, with the strength set by the damage since the last pulse. iPhone uses the Taptic Engine through a small native plugin; Android uses a short timed vibration. Why not `Handheld.Vibrate()`: it is one long buzz with no strength control.

## 13. Arena scale: sizes and ranges follow the lane gently (added 2026-10-22)

### What scaled before this change

Only things defined as fractions of the lane scaled: unit speed (lane length divided by seconds to cross), bridge positions and widths, lane and island width, the funnel and the summon zone, and the positions sent between phones. Everything defined in metres stayed fixed.

### What was done

One number, **arena scale**, now multiplies the distances that were fixed in metres:

`scale = (lane length / reference lane) ^ exponent`, limited to a minimum and maximum.

Defaults: reference lane 2 m, exponent **0.5** (square root, a gentle curve), minimum 0.7, maximum 1.8. At your current 2 m lane the scale is exactly 1, so **nothing changes at 2 m**.

| Lane length | Scale | Unit height (0.15 m at 2 m) |
| --- | --- | --- |
| 1 m | 0.71 | 0.11 m |
| 2 m | 1.00 | 0.15 m |
| 3 m | 1.22 | 0.18 m |
| 5 m | 1.58 | 0.24 m |

With the square root, units look about 1.6 times faster in body-lengths per second at 5 m than at 2 m, where fully scaling the size would keep it the same and not scaling would make it 2.5 times faster. The exponent is the one setting that controls this: 0 never scales, 1 scales fully, 0.5 is the gentle middle.

**Scaled:**
- Unit height and the spawn effect.
- Melee reach (`Engage Range Meters`), tower clearance, disengage gap and look-ahead on `MatchState`.
- Every unit's attack range (the Mage's 0.35 m is multiplied when the unit is created).
- Tower size and footprint (`TowerController`), and so the tower stand-off, the bubble layout and sizes, and where your tower stands in front of you.
- Lightning radius (the real hit area, the cursor's area marker and the strike effect) and the height of the bolt.
- Ranged bolt size and speed, the tower aim height, the summon marker size and the aim reach.
- The bridge's fallback deck height.

**Not scaled** (real-world values): tag size, tag-to-ground offset, floor height, bubble lock distance and angle, the screen crosshair and the HUD.

**When the scale is set:** it follows the live lane smoothly (0.4 s) while you set up, and is frozen when the match starts, so nothing resizes mid-game. Each phone uses its own scale for what it draws; only the host's scale decides combat.

| File | Change |
| --- | --- |
| `Match/MatchState.cs` | New "Arena scale" fields (reference lane, exponent, minimum, maximum, smoothing). `ArenaScale`, `ScaledLightningRadius`. Engage range, clearance and hysteresis are scaled. |
| `MatchState.Geometry.cs`, `.Combat.cs`, `.Economy.cs`, `.Spells.cs` | Freeze at capture. Look-ahead, stand-off, attack range and lightning radius use the scale. |
| `Gameplay/GameStateRenderer.cs` | Unit height, spawn effect, bolt size and speed, and tower aim height use the scale. |
| `Gameplay/Towers/TowerController.cs` | Tower size, footprint radius, own tower offset and tower height (used by the bubbles) use the scale. |
| `Gameplay/SpellCaster.cs`, `Input/SummonCursor.cs`, `Environment/BridgeVisualizer.cs` | Lightning radius, bolt height, marker size, aim reach and fallback deck height use the scale. The cursor now reads the lightning radius from `MatchState`. |

### What you need to do

1. Let Unity compile. Select the object with `MatchState` and look at the new **Arena scale** section. The defaults need no change.
2. Test at your normal 2 m lane first: it should look exactly as before.
3. Then change the lane (move the fake opponent in the debug menu, or play in a smaller or larger space) and check that units, towers, ranges and the lightning area get bigger and smaller together.
4. If units still look too fast or too slow in a big arena, change **Arena Scale Exponent** on `MatchState` (higher follows the size more). Change the minimum and maximum if the extremes look wrong.
5. The values you already tuned (0.2 m melee reach, 0.35 m Mage range, 0.25 m lightning radius, 0.15 m unit height) now mean "at a 2 m lane".

### Trade-offs

- With the gentle curve, ranges in a big arena are a smaller share of the lane than at 2 m (a 5 m lane has a melee reach of about 6% of the lane, against 10% at 2 m). Fights in big arenas are a little less crowded. A higher exponent fixes that but makes units bigger.
- The scale depends on the measured lane length, which depends on the tag size calibration (0.119 on your iPhone). A wrong tag distance gives a wrong scale, so calibrate the tag first.
- Not run in Unity. It type-checks only.

## 16. Notice range and hit reach: units now chase (added 2026-10-22)

### What changed

Before, one number (`Engage Range Meters`) was notice, stop and hit distance at once, and units never left their path to reach an enemy. Now:

| Setting | Meaning | Default |
| --- | --- | --- |
| `Notice Range Meters` (the old Engage Range, same saved value) | How far away a unit notices an enemy unit and starts walking toward it | 0.4 |
| `Hit Reach Meters` (new) | How close a melee unit must get before it hits | 0.15 |
| `Attack Range Meters` (per unit, `UnitStatsTable`) | A ranged unit's own hit distance (Mage 0.35) | 0 = melee |

Everything is multiplied by the arena scale, like the other distances.

### How it behaves

1. A walking unit checks for enemy units within its notice range. A ranged unit notices at least as far as it can shoot. Enemies across the water on a different bridge are ignored (a ranged unit may still shoot across the water if the enemy is inside its attack range).
2. If the nearest enemy is inside the unit's hit reach, it stops and attacks.
3. If it is noticed but still too far, the unit walks straight toward it at its normal speed (it stops just inside its reach). It keeps chasing the same enemy while that enemy stays inside the notice range plus a small gap, and drops it when it moves further away or dies.
4. A unit that is attacking and sees its target move beyond its reach (plus the gap) starts chasing it again. Before, melee units kept hitting a target that had walked away.
5. Towers are unchanged: a unit stops at the tower stand-off and attacks it, and a unit already attacking a tower does not switch to a nearby enemy unit.
6. Chasing units are still kept inside the arena, so they cannot leave a bridge or cross the water.

Why it helps: a Mage (reach 0.35) now clearly out-reaches a melee unit (0.15), so it fires first while the melee unit closes in, which also fixes the earlier case of an enemy Warrior walking past a Mage.

### How damage is calculated when there is more than one target

- **One target per attacker.** Each unit locks onto a single enemy (the nearest one when it first notices) and deals `Attack DPS x 0.1 s` to that one unit on each 0.1 s tick, as long as it stays within reach. There is no splash damage and no damage to the other units nearby.
- **Many attackers, one target.** Their damage adds up on that target.
- **Many enemies in reach.** The unit does not switch to a closer or weaker one. It stays locked until its target dies or leaves its reach, and then picks the nearest enemy on the next tick.
- **Overkill is wasted.** Damage past 0 HP does not carry over to another unit.
- **Order inside a tick.** Units act one after another in spawn order. A unit that has already been killed earlier in the same tick does not get to hit back, so older units have a very small edge in a tie.
- **Towers.** Each unit attacking a tower removes its own Attack DPS from the tower, and takes 15 damage per second of counter-damage itself. Several attackers each take that counter-damage separately.
- **Lightning is the only area attack.** It damages every enemy unit inside the radius at once (full damage at the centre, `Edge Damage Fraction` at the rim), plus the tower if it is in range.

### What you need to do

1. Let Unity compile. The old `Engage Range Meters` value is kept: it is carried over to `Notice Range Meters`.
2. Look at `MatchState` > Lane engagement: **Notice Range Meters** (0.4) and the new **Hit Reach Meters** (0.15). Tune them. The Debug menu's Match label shows both live values.
3. Test in VS CPU: spawn units on both sides and watch them walk toward each other and stop at the hit reach. Spawn a Mage and a Warrior together: the Mage should stop and fire while the Warrior walks in.
4. Watch for units wandering oddly, getting stuck at the edge of a bridge or jittering between chase and attack. Tell me what you see.

### Risks

- It is new movement and has not been run. Chasing can pull units off their usual path and out of the formation they had.
- Two units of the same speed chasing each other never catch a retreating target. This is expected.
- Melee units now close to 0.15 m, and the model scale is 0.25 m tall, so they should look like they are touching. Raise Hit Reach if they overlap.

## 19. Fireball (built 2026-10-27, replaces Overcharge)

Decisions: Fireball **replaces Overcharge**; cost **6 mana** (first 7, lowered 2026-10-27); it flies to the aim point like Lightning (it does not stop for units on the way); the numbers are the ones from the plan (below), with a **burning floor** added.

### What it does

1. You aim with the crosshair (the same aim as Lightning, anywhere in the arena) and cast it from the Fireball card, the Debug menu or the glove.
2. A ball leaves **your tower** and flies along a low arc to the aim point. The flight takes the distance divided by 1.2 m/s (about 0.8 s over 1 m, never less than 0.4 s, and the speed scales with the arena). A marker on the floor shows where it will land, in orange for your fireballs and red for the enemy's, so the defender can see it coming.
3. On arrival it explodes: **120 damage** to enemy units at the centre (**60** at the edge of the radius), **40** to a tower in range. Radius **0.12 m**, scaled with the arena.
4. The floor then **burns for 4 s**: every enemy unit standing in the patch takes **12 damage per second** while it is in it. Embers rise off the patch and it flickers and fades out.
5. Mana is spent only if the aim is valid, like Lightning, so a miss costs nothing.

| | Lightning | Fireball |
| --- | --- | --- |
| Cost | 5 | **6** |
| Hits | After a 0.5 s telegraph, instantly | After a flight of about 0.8 s, can be seen coming |
| Area | 0.2 m, 180 (90 at the rim) | 0.12 m, 120 (60 at the rim) |
| Tower | 60 | 40 |
| Afterwards | Nothing | Burning floor, 12 per second for 4 s |

All of these are Inspector fields on `SpellCaster` under "Fireball" and are registered in the one shared `SpellSpec`, so the host uses the same numbers for a client's cast.

## 24. Player 2's units walk backwards or sideways (found and fixed 2026-10-27)

Player 2's phone is the client: it does not run the game, it only draws what the host sends. Reading the code, there were four causes for units looking wrong on that phone:

1. **The host never told the client which way a unit faces.** The client guessed by looking at how the unit moved between two updates. A unit that stood still (attacking, or waiting) kept an old direction, so it did not face its target, and a unit that was only just created faced the world's forward direction (not the lane) until it had moved. That looks like facing sideways or the wrong way.
2. **The guess ignored slow movement.** It only turned a unit if it had moved more than 1 cm between updates. Slow units (Tank) or a small arena move less than that, so they never turned at all. (The host had the same 1 cm limit.)
3. **The client's clock did not run.** Smoothing between two host updates uses the time since the last update, and the client's copy of that clock stayed at zero. So the client drew every unit at its *previous* update's position, one step behind, moving in small jumps with no smoothing. A unit that stops, or changes direction when it chases (new chasing movement), can then look like it steps backwards or sideways.
4. **Turning was instant.** Every update snapped the unit to its new direction, so small changes in direction between updates showed as shuffling.

### What was changed

| File | Change |
| --- | --- |
| `Networking/NetworkMessages.cs` | Each unit in the update now carries `faceAlong` and `faceLat` (its facing as a direction along and across the lane, like the position fields). |
| `Match/MatchState.Network.cs` | The host sends its real facing (the one it also uses when a unit turns to its target or the tower). The client turns the unit exactly that way, in its own frame, when it creates the unit and on every update. An older host that does not send it falls back to the movement guess, with the limit lowered to 1 mm. |
| `Match/MatchState.cs` | The client's clock now runs, so units glide between updates instead of jumping. |
| `Match/MatchState.Combat.cs` | The host's turn threshold lowered from 1 cm to 1 mm, so slow units and small arenas still turn. |
| `Gameplay/GameStateRenderer.cs` | A new unit appears already facing the right way, and turning is smoothed instead of snapping (applies to both phones). |

### What you need to do

1. Let Unity compile. Both phones must be on this version (the host sends the new field).
2. Play a two-player match and watch Player 2's phone: units should face the way they walk, face their target when they fight, and glide smoothly. Check a Tank (slowest) and a chasing unit.
3. If something is still wrong, tell me what the unit does (for example walks backward while facing forward, or turns late) and on which phone, and I will look at that case.
